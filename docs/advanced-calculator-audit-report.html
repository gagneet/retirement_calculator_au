Australian Retirement Calculator Audit

Main calculator and Monte Carlo review

The calculator is strongest in Pipeline A for tax, contributions, and enhanced Monte Carlo, but the overall advanced experience is weakened by three different calculation engines that silently disagree with each other. The most serious errors are in the life-simulation pipeline, where Age Pension and retirement cashflow are mis-modeled in ways that can materially overstate portfolio durability or understate pension eligibility.

1. What the advanced calculator is doing today

Main execution points: src/js/app.js:578-832, src/js/app.js:1031-1133, src/js/app.js:5829-5921, src/js/app.js:6437-6548.

Main advanced calculator workflow
  1. Read inputs: ages, salary, super, savings, property, trust, healthcare, pension overrides, simulation settings.
  2. Validate: ages, allocations, negative values, basic plausibility.
  3. Main projection: simulator.simulateRetirement() generates deterministic balances and cashflow.
  4. Main Monte Carlo: runEnhancedMonteCarloSimulation() applies regime-aware, year-by-year return paths.
  5. Life Simulation tab: runFullSimulation() uses a different engine with separate pension/tax logic.
  6. Render: summary tabs, charts, recommendations, export.
What is going well
  • Tax brackets, LITO, Medicare levy, MLS, and Division 293 are mostly well handled in the main pipeline.
  • Concessional caps, transfer balance cap gating, minimum drawdowns, trust attribution, and state land-tax tables are solid.
  • The enhanced Monte Carlo engine has the best technical design in the app: correlated asset shocks, regime shifts, and volatility clustering.
  • The advanced form already captures a wide range of materially useful fields.

3. Main advanced calculator overview: what is missing

Super rules missing or incomplete
  • Preservation age should be derived from DOB, not assumed from current age.
  • Carry-forward concessional caps are not modeled.
  • Non-concessional bring-forward rules are not modeled properly.
  • Taxable vs tax-free super components are not tracked.
  • Pension-phase earnings tax treatment is not separated from accumulation-phase tax.
Age Pension rules missing or incomplete
  • Deeming is not consistently used.
  • Work Bonus is not modeled.
  • 12-month home-sale proceeds treatment for downsizing is not modeled.
  • Pension thresholds are treated as static instead of indexed over time.
  • Grandfathered deeming treatment for pre-2015 pensions is absent.
Cashflow and risk gaps
  • No explicit actual household budget field in the main life-sim path.
  • No life-table or sex-based longevity model.
  • Aged care is simplified to a probability and annual cost, not means-tested pathways.
  • Property model lacks acquisition cost/date and more detailed tax offsets in every path.
  • Documentation pages drift from code and law.

Missing fields that would materially improve prediction quality

Missing field Why it matters Recommended use
Date of birth for each adult Needed for preservation age, pension timing, and age-specific rules. Replace age-only access assumptions with DOB-driven super access logic.
Actual monthly household expenses Much more important than salary-proxy expense heuristics. Use as the base for accumulation and retirement spending transitions.
Unused concessional cap history Carry-forward caps can change contribution strategy materially. Model up to 5 years of unused concessional caps where eligible.
Property purchase date and cost base Essential for CGT and true after-tax sale proceeds. Track acquisition cost, improvements, and purchase year.
Super taxable / tax-free component split Affects death benefits and some withdrawal-tax edge cases. Track component balances through time.
Deeming status / grandfathering flag Important for some pension income-stream cases. Apply grandfathered actual-income treatment where appropriate.
Work bonus bank / planned work in retirement Changes pension outcomes for part-time working retirees. Model fortnight work income and Work Bonus balance.
Sex / actuarial longevity preference Longevity risk is not well handled by a single fixed lifespan input. Offer fixed age, confidence age, or ABS life-table mode.

4. Australian retirement rules that should anchor corrections

Rules already present and worth keeping
  • SG at 12% from 1 July 2025.
  • Concessional cap at $30,000.
  • Transfer balance cap logic in the main simulator.
  • Minimum pension drawdown schedule.
  • Medicare levy, MLS, LITO, Division 293 in the main path.
  • Trust attribution and homeowner vs non-homeowner asset thresholds.
Rules that need stronger implementation
  • Age Pension deeming on financial assets.
  • Age Pension means testing should use the lower of income-test and assets-test outcomes consistently in all engines.
  • Super access should be preservation-age and condition-of-release aware.
  • Contribution-cap rules should be fully versioned and shared from one source.
  • Future pension thresholds should be indexed rather than frozen.
Known config drift: src/js/config.js:216-224 still shows a non-concessional cap of $110,000, while src/js/contribution-calculator.js:10-17 uses $120,000. That should be versioned in one place only.

5. Incremental workflow to make the calculator materially more accurate

Phase 1 — immediate fixes
  1. Fix Pipeline B pension means testing: remove actual super withdrawals from assessable income; apply deeming instead.
  2. Subtract pension before calculating super withdrawal need.
  3. Restore retirement investment income on non-super assets.
  4. Apply partner contributions tax and Division 293 consistently.
  5. Update stale pension thresholds in simulation_engine/pension_engine.js.
Phase 2 — structural fixes
  1. Create a single versioned policy layer for pension, tax, caps, deeming, and drawdowns.
  2. Refactor Pipeline B and Pipeline C to consume the same policy/rules layer as Pipeline A.
  3. Replace heuristic expense inference with explicit household budget inputs.
  4. Align all Age Pension calculations on one means-test engine.
  5. Disclose which engine each tab is using until unification is complete.
Phase 3 — prediction quality upgrades
  1. Use year-by-year return sequences everywhere Monte Carlo is offered.
  2. Add ABS life-table mode or confidence-age mode for longevity.
  3. Add property cost-base inputs and tax-aware sale proceeds.
  4. Model carry-forward concessional caps and NCC bring-forward rules.
  5. Index pension settings over time rather than freezing them.
Phase 4 — validation workflow
  1. Create golden test cases from official ATO and Services Australia examples.
  2. Test single, couple, one-partner-eligible, homeowner, renter, downsizer, and trust scenarios.
  3. Test high-income Division 293 and low-income LISTO/co-contribution cases.
  4. Compare deterministic output vs Monte Carlo medians for consistency.
  5. Refresh legal thresholds on a versioned release schedule.

6. Practical improvement plan for final retirement outcomes

What to keep
  • Main pipeline tax framework.
  • Enhanced Monte Carlo design in enhanced-monte-carlo.js.
  • Trust, property, franking, and contribution logic in the main simulator.
  • Broad advanced form coverage.
What to retire or merge
  • Standalone pension thresholds in simulation_engine/pension_engine.js.
  • Standalone rule set in advanced-design-engine.js.
  • Any tab that silently uses a different pension or tax model than the main result.
  • Heuristic-only spending proxies where a real input can be collected.
